## 3. The findings that matter

### F-01 — Critical: overlapping batches corrupt rotation state

**Evidence (traced + code):**
`src/lib/lanes/freshTextCard.ts:58,97`, `src/lib/lanes/recombination.ts:138,146`,
`src/lib/textBank.ts:99,102`. Every lane does read-modify-write:

```
read pointer → select base → render → write pointer+1
```

**Why it matters:** the cron (`vercel.json`) and the home page's "Run batch"
button are *both* live triggers. Two batches overlapping — cron firing while D
taps, or a Vercel retry — read the same pointer, select the **same base asset**,
render it twice, and both advance to the same next index. That is duplicate
renders against an **append-only** gallery, permanently skipped assets, and
duplicate Printify/AI spend. Nothing in the code or the schema prevented it. The
tests can't catch it (they are single-threaded), and it fails silently.

**Fix shipped:** `supabase/migrations/004_batch_runs.sql` adds `batch_runs` with
a **partial unique index** `(brand) where status='running'` — the database is the
authority, exactly like the finality indexes. `/api/batch` claims a row before
assembling; a second concurrent claim gets `23505` → **409
`batch_already_running`** with the age of the live run. `src/lib/batch/batchLock.ts`.

Three deliberate design details:
- **Stale locks self-heal.** A killed serverless function never finalizes its
  row; without a staleness window the brand would be locked out forever — worse
  than the race. Runs older than 15 min are retired (guarded `UPDATE` on the
  exact row, then one claim retry). Escape hatch: "release" in `/setup`.
- **Missing migration degrades loudly.** If `batch_runs` doesn't exist, the
  batch still runs — D must not be blocked from his own pipeline by an unapplied
  migration — but the response carries `lock.status='unavailable'` + reason, the
  server logs an error, and `/setup` shows it red.
- **Closes out on both paths.** Success → `done` + queued count; throw → `error`
  + message. Best-effort, never throws into the route.

Pinned by `tests/batchLock.test.ts` (11 tests: free slot, live run → 409 with
nothing run, stale retirement, unavailable-not-throwing, finalize on success and
on error).

### F-02 — Critical: a batch that produced nothing, but didn't

**Evidence (executed):** I ran the real oracle over the shipped text banks:

```
$ npx tsx .oracle-probe.ts
=== misfit (lane fresh_text_card) ===
  [2] FAIL (13w) theology_absence_in_long_text :: You are not too broken. You are exactly the material He works with.
  [4] FAIL (11w) theology_absence_in_long_text :: The lost sheep is the one He leaves the ninety-nine for.
  [7] FAIL (11w) theology_absence_in_long_text :: He did not come for the healthy. He came for you.
  -> 3/10 placeholder lines ORACLE-REJECTED for misfit
=== forge ===
  -> 0/10 placeholder lines ORACLE-REJECTED for forge
```

Those lines exceed the 10-word threshold and contain no voice keyword. So on day
one, **30% of misfit fresh-text items are queued as oracle-rejected**… and
`/api/review` **excludes** oracle-failed items from D's default view, `/review`
had no toggle for it, and the only signal was a count on the dashboard. Net
effect: "I ran a batch and nothing showed up." That is precisely the invisible
silent failure this project forbids everywhere else.

**Fix shipped:**
- `/review` gains a **"Show oracle-rejected items"** toggle (the API already
  supported `includeRejected=true`; nothing ever sent it) and an explicit
  message when the fetch 401/403s.
- The dashboard now shows an amber banner: *"N item(s) hidden by the oracle —
  they are in the queue, not lost"*, linking straight to Review.
- `/setup` reports the split (`passed` vs `rejected`) as its own check and runs
  the same audit over `textBanks.ts`, so the number is visible before the first
  batch rather than after.

**Still on D:** the real fix for the *content* is your words (see F-05) and a
keyword list that reflects them.

### F-03 — High: upload validation trusted the client

`src/app/api/gallery/route.ts` validated `file.type` — a string the client
chooses — then uploaded the raw bytes with `contentType: file.type` into a
**public** bucket. A writer-allowlisted client (or anyone holding a token) could
store arbitrary content (HTML, for instance) under a `.png` key with a
content-type of their choosing, served from the storage domain.

**Fix shipped:** the buffer is now decoded by `sharp` before upload; the declared
MIME must agree with the sniffed format, the extension is derived from the
sniffed format, and the stored `contentType` is the sniffed one. Undecodable
bytes → 415. (`runtime = 'nodejs'` declared explicitly.)

### F-04 — High: `Remix` is a button that lies

**Evidence (executed grep):** `remix_queue` is written in exactly one place
(`src/lib/review/reviewQueue.ts:115`), counted in one place (`/api/status`), and
**read by nothing else**. There is no processor, no UI, no lane that consumes
it. `processed` is `default false` and no code ever sets it true.

So the three-button UI makes a promise two of three buttons keep. D taps Remix
and the item disappears from his queue forever and lands in a backlog nobody
will ever look at.

**Why this is a red-team finding and not a nitpick:** the governance model says
"silent failure is forbidden; every error surfaces". A backlog that silently
never drains is the same failure with a nicer UI.

**Options (D's call, deliberately not decided for him):**
1. **Label it honestly today** — rename the button to `Remix (queued)` and add a
   line in Review: "N remix work orders waiting; no processor exists yet."
   Zero risk, zero new semantics.
2. **Wire the loop** — a `/api/remix/next` that pops the oldest unprocessed row
   and re-runs its lane as a new queue item. This is real work (new lane
   orchestration + a re-queue path) and it touches the decision-handler
   invariants, so it should not be a same-day change.

I did **not** implement either. What I did do: `/setup` and the dashboard show
the remix backlog count, and this document names it.

### F-05 — High: placeholder brand voice was shipping-eligible and invisible

`src/config/textBanks.ts` and `src/config/doctrine.ts` carry model-written
placeholders with a screaming comment block — and nothing in the codebase could
tell. Combined with F-02, the placeholders also *change pipeline behaviour*: the
voice-keyword list decides which long texts get rejected, so a placeholder list
silently governs what reaches review.

**Fix shipped:** two honest flags —
`TEXT_BANKS_ARE_PLACEHOLDER` and `DOCTRINE_IS_PLACEHOLDER` (both `true` in the
repo) — surfaced in `/setup` as a **failing, blocking check** with the oracle
audit of the shipped lines attached. Flip them only when the words are yours.

This is an honesty flag, not a control: it cannot detect that you pasted a
placeholder back in. It can stop the pipeline from *looking* ready while the
words are borrowed.

### F-06 — High: reads were public

`/api/review` had no auth: unreleased brand copy, image URLs and queue internals
were one guessed URL away (`/api/review?brand=misfit&includeRejected=true`).
`/api/gallery` GET lists the entire asset store, including `approved_post`
entries that were never posted anywhere.

**Fix shipped:** `/api/review` now requires the writer allowlist (fails closed
on an empty list — same rule as every write). The review page already only
fetched with a session, so the operator cost is zero; it now sends the token.

**Not changed, deliberately:** `/api/gallery` GET stays public (dossier §5.16
specifies a public listing — it is the marketing asset store), and
`/api/status` stays public so the dashboard renders its config chips before
sign-in (F-17). If the gallery should not be world-readable,
`GALLERY_WRITER_IDS`-gate it the same way `/api/review` is gated — a
ten-line change, but it is a product decision, not a bug fix.

### F-07 — High: nothing had ever been verified end to end

The DEBUG-REPORT is a list of failures that all passed the tests: a cron that
could never fire, a renderer with phantom fields, a lane that re-rendered the
same base forever. The pattern is consistent — **static verification keeps
missing whole classes of failure**, and the `oracle_result->>passed` filter is
still sitting there explicitly marked UNVERIFIED.

**Fix shipped:** the `/setup` page does live verification with the production
code paths:

| Step | What it actually proves |
|---|---|
| 1 Sign in | The phone can get a session; your user id, and whether it is in the allowlist |
| 2 Database | Every table, row count, and **the jsonb path filter** — the one known-unverified live check |
| 2b SQL paste-back | Triggers, unique indexes and RLS, which the REST API genuinely cannot see |
| 3 Storage | Service-role write → **public** HTTPS read → cleanup (catches a private bucket before every render fails) |
| 4 Smoke render | The **real** `sharpRenderer`: canvas → upload → fetch → typography → composite → webp → upload → fetch. Shows the card so you can judge the typeface |
| 5 Catalog | One live Printify search |
| 6 Base assets | Eligible base counts per lane, with deep links to upload the right category |
| 7 Batch | Runs it, claims the lock, reports per-lane outcomes and the run log |
| 8 Loop | Newest approved item: decision row → gallery row (same id) → queue closed → **idempotent replay returns the same record** → still exactly one gallery row |

Step 8 is the one I'd point at: it exercises the documented crash-recovery path
from dossier §3 against live data and structurally cannot create a second
decision, a second gallery row or a remix order — those are the properties under
test. Nothing in `/setup` writes to `gallery_assets` except the explicitly
armed, separately-labelled backdrop button (guarded: refuses unless the brand has
zero eligible bases).

### F-08 — Medium: the merch hierarchy's cheapest tier is unreachable from a phone

**Evidence (traced):** `tagOverlapMatcher` returns `undefined` for a tagless
query — by contract. `gallery_assets.tags` is read by `rowToAsset` but **written
by no application code path except `scripts/seed.ts`**, which bypasses
`addToGallery` with a direct insert and a comment saying so. `POST /api/gallery`
never accepts a tags field, and `addToGallery(store, asset)` cannot carry one
because the frozen `GalleryAsset` type has no `tags`.

**Consequence:** every asset D uploads from his phone has `tags = '{}'` →
tier 1 (`gallery_reuse`) can never fire → merch items fall to the catalog, and on
an empty catalog result to `ai_touchup`, the deliberate **paid last resort**. The
cost-control rationale in dossier §1 quietly inverts for anything D uploads
himself. The DEBUG-REPORT fixed the *code* side of this bug (Bug 4) but not the
data side.

**Options:** (a) accept `tags` in the gallery upload form and pass them through
an extended store method; (b) add a tags field to the frozen `GalleryAsset` type
(the dossier forbids renaming, and this is additive, but it is a type-surface
decision); (c) generate tags in the UI from the file name. I did not pick one —
each touches a frozen surface or a product decision.

### F-09 — Medium: "permanent" gallery rows can point at Printify's CDN

`src/lib/orchestrator.ts:127-140` uses `candidate.productUrl` as the merch
item's `imageUrl`. Approving that item runs `onPostApproved`, which writes a
`gallery_assets` row with `url = <Printify CDN URL>`, `permanent: true`,
`source: generated_and_approved`. Two consequences:

1. The append-only "permanent" store can contain third-party URLs that expire or
   change — the one thing the word permanent must not mean.
2. For `gallery_reuse` candidates the *same* image is inserted a second time
   under a new id, so the gallery holds duplicates and recombination can later
   pick the copy.

**Sensible fix:** re-host the image into the bucket at decision time (fetch →
upload → store our own URL), or refuse to `post` a merch item that has no
self-hosted image. Both change decision-path behaviour, so neither is a
same-night change on an append-only table.

### F-10 — Medium: the brand typeface has never once rendered

**Evidence (executed, in this sandbox):** I ran the real overlay path
(`buildSvgOverlay` → `sharp().composite().webp()`) and produced a 1080×1080 card.
`BRAND_TYPOGRAPHY.misfit.fontFamily` is `"Space Grotesk, system-ui, sans-serif"`;
the rendered glyphs are a generic sans fallback (double-storey `g`, uniform
stroke — not Space Grotesk's letterforms). `fc-list` reports **zero** fonts in
this environment; librsvg resolved to a built-in fallback and **said nothing**.

That is the same failure shape as the phantom `.font/.size/.scrim` fields the
dossier warns about: brand voice silently not applied, everything green.

**Surfaced, not fixed** — and deliberately so: I cannot see Vercel's font list
from here, and inventing a fix (bundling a TTF + `FONTCONFIG_PATH`) would itself
be unverified. `/setup` step 4 exists so you can look at a real card on your own
deployment in ten seconds and decide between:
(a) set `fontFamily` in `doctrine.ts` to a font that is actually installed in the
runtime (honest, zero-dependency, keeps the design consistent), or
(b) commit the font + a `fonts.conf` and wire `FONTCONFIG_PATH`/`FONTCONFIG_FILE`
so the branded face is guaranteed everywhere.

Either way: after (a) or (b), the next smoke render is the proof.

### F-11 — Medium: one mis-tap is permanent, and a frame can trigger it

Decisions are irreversible by design. The review page can be framed by any
third-party page, and the three decision buttons are big thumb targets. There is
no `frame-ancestors`, no `X-Frame-Options`.

**Not applied on purpose.** `Content-Security-Policy: frame-ancestors 'none'` /
`X-Frame-Options: DENY` breaks every embedding host — including the in-browser
preview this app is developed in. Shipping it silently would have broken your
preview and looked like my change had broken the app.

**Paste this into `next.config.ts` the day the app is served on its own domain:**

```ts
async headers() {
  return [{
    source: '/:path*',
    headers: [
      { key: 'X-Frame-Options', value: 'DENY' },
      { key: 'Content-Security-Policy', value: "frame-ancestors 'none'" },
    ],
  }];
}
```

What I *did* apply is safe everywhere and cannot break rendering:
`X-Content-Type-Options: nosniff`, `Referrer-Policy:
strict-origin-when-cross-origin`, `X-DNS-Prefetch-Control: off`.

### F-12 — Medium: batches had no memory

If a scheduled batch failed, nothing recorded that it had run — which is exactly
how a triple-broken cron went unnoticed for weeks (DEBUG-REPORT Bug 2). The
dossier defers `event_log`; `batch_runs` (F-01) is the minimum viable version of
it: brand, status, started/finished, queued count, error note. `/setup` shows the
last 12 runs with a release button for a stuck one.

- **F-13:** `CRON_SECRET` was compared with `===` in two places. Now
  `timingSafeEqual` (length-checked — the length of a valid secret isn't secret).
  Pinned by the existing cron-contract tests still passing.
- **F-14:** added `src/app/robots.ts` — `/setup`, `/review`, `/api/` disallowed.

- **F-15:** the browser Supabase client existed in **three** copies
  (`lib/browserSupabase.ts`, `review/page.tsx`, `gallery/page.tsx`). One of those

- **Same pass:** the queue-row → `ReviewItem` mapping (the thing whose absence

### F-16 / F-17 — Accepted risks (documented, not fixed)

- **F-16:** `supabaseTextBankProvider.pick` advances `text_rotation_state`
  *before* the render, so a failed render silently consumes a line. Cosmetic
  (rotation only, no data loss) and the fix would change a frozen interface.
- **F-17:** `/api/status` returns counts and raw DB error strings without auth.
  Deliberate: the dashboard must render config chips before sign-in. The
  information is operational, not secret. Revisit if the deployment URL ever
  becomes public with a real audience.

### F-18 — Info: cron is UTC and the two brands used to fire at the same minute

`0 8 * * *` is **03:00** in Baton Rouge, not 8am. Both brands fired in the same
minute, which is what made F-01 exploitable on a schedule. Now `0 8` (misfit) and
`20 8` (forge) — and with the lock, same-minute would be safe anyway. Note that
Vercel's plan limits decide how precisely crons actually fire; `vercel.json` and
the plan should agree.

## 5. What `/setup` cannot do, and why (stated on the page itself)

1. **It cannot set your Vercel environment variables.** Secrets belong in the
   deployment config, not a web form that writes them into a database. It shows
   the exact value with a copy button instead.
2. **It cannot read Postgres triggers or indexes** through the REST API, and a
   per-row probe insert would pollute an append-only table forever. So: exact SQL
   with a parsed paste-back. The append-only proof runs inside a transaction that
   is always rolled back.
3. **It cannot tell you whether a card looks right.** That judgement is yours;
   step 4 exists so you can make it in ten seconds.

## 6. Your move — the live checklist

1. Apply `supabase/migrations/004_batch_runs.sql` (Supabase → SQL Editor).
2. Redeploy with `GALLERY_WRITER_IDS` = your user id (Setup step 1 prints it with
   a copy button — no dashboard spelunking).
3. Open `/setup`, press every button, and read the red ones.
4. Run the SQL paste-back and the append-only proof; paste the JSON back.
5. Step 4 smoke render: **look at the card** and decide on F-10.
6. Upload a base or two (`/gallery?brand=misfit&category=atmosphere`), run a
   batch, approve one item, then run step 8.
7. Replace `doctrine.ts` + `textBanks.ts` with your words, flip both flags, and
   re-run the `/setup` audit until the oracle stops rejecting your own lines.
8. "Copy setup report" at the top of `/setup` and send it back — it contains
   every result, so the next round starts from facts instead of guesses.

## 7. Reproduce my verification

```bash
npx tsc --noEmit                  # clean
npm test                          # 109 passed (11 files)
npm run build                     # compiles, 11 routes
npx next start -p 3000 -H 0.0.0.0 # then: /setup → 200, POST /api/setup → 401 without a token
```

The oracle audit of the shipped text banks (F-02) was run with a throwaway
script that imported the real `runPrefilter`, `TEXT_BANKS` and each brand's
`fresh_text_card` lane, and printed the rejected lines with their reason strings.
The render proof (F-10) ran the real `buildSvgOverlay` through
`sharp().composite().webp()` and produced a 1080×1080 card — the typeface in it
is not the requested one, and no error was raised anywhere.
